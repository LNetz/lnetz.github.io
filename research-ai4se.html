02AI-driven Software Engineering

article · 2024, revised 2026

What is this “new” AI, how does it work — and where does it actually help in building software? An introduction from neurons to agents and language models that write models.

Series · part 1: Model-driven SEpart 2: AI-driven SEpart 3: Digital twinspart 4: Evolutionary algorithms

How an LLM worksBasic termsLLMs and model-driven engineering

Artificial intelligence is not a new topic. As early as 1950, Alan Turing introduced what would later be called the Turing test in his paper Computing Machinery and Intelligence [1]. Less than a decade later, the first neural networks followed [2].

I propose to consider the question, “Can machines think?”

Alan M. Turing · Computing Machinery and Intelligence, 1950

It took several more decades until 2017 laid the foundations for large language models (LLMs) [3]. Because they handle natural language so well, LLMs can be used for almost anything. You need not be an AI specialist or a computer scientist to work with them: an LLM places hardly any restrictions on its input and grasps its meaning remarkably well.

Three questions follow, and they give this article its three parts: how does such a model work? Which terms do you need to talk about it — up to agents and harnesses? And where can we put it to productive use in software engineering, with models?

01How an LLM works

An LLM is a neural network that has learned one thing extremely well: to continue a text. Everything else — answering, translating, writing code — follows from that.

How a neural network decides

The basis of every LLM is a neural network. The idea is easiest to see with a picture: is this a dog or a cat? The network does not see a dog, only pixel values. Each pixel is an input; each input is connected to neurons with a weight; each neuron adds up its weighted inputs and passes the result through an activation function to the next layer. At the end, two output neurons compete — “dog” and “cat”. During training, the weights are adjusted over many examples until the right neuron wins.

For scale: the roundworm C. elegans gets by with 302 neurons and about 7,000 synaptic connections. GPT-3 has 175 billion weights [8]; current LLMs are on the order of a trillion.

For the curious
  • How the weights move. After each example the network compares its output with the right answer. Backpropagation works out, layer by layer from the back, how much each weight contributed to the error [13]; every weight is then nudged a tiny step in the direction that makes the error smaller (gradient descent). Repeat that billions of times.
  • Pre-training. An LLM needs no labelled pictures: the right answer is simply the next token of a real text. That is why it can learn from almost everything ever written [5].
  • Becoming an assistant. A pre-trained model only continues text. Chat models get a second phase: people rank answers, a reward model learns those preferences, and the LLM is tuned towards them (RLHF). In the InstructGPT study, people preferred the answers of a tuned model with 1.3 billion weights over those of GPT-3 with 175 billion [14].

Generative AI and the transformer

Generative AI means systems trained to create content that is hard to tell apart from human work — text, images, music and even code. Examples are GPT-4 (Generative Pretrained Transformer) for text, DALL-E for images and Codex for programming. All of them rest on the transformer architecture.

Two aspects make the difference. First, the neural network is trained on text in a way that captures not only the position of words but how they relate to each other. That lets a GPT resolve references — including implicit ones:

The second aspect is the sheer amount of training. LLMs are trained on enormous amounts of data and therefore handle the nuances of human language very well. Input may be ungrammatical, misspelt and colloquial — the model has seen all of that before.

For the curious
  • What attention computes. Every token is turned into three vectors: a query (what am I looking for?), a key (what do I offer?) and a value (what do I pass on?). A token compares its query with the keys of all earlier tokens; the better they match, the more of their value it takes in [3]. That is how “she” can find the carriage.
  • Many heads, many layers. Several such attention “heads” run side by side, each free to learn a different kind of relation, and the layers are stacked — 96 of them in GPT-3, each 12,288 numbers wide [5].
  • The context window. Because every token looks at every earlier one, the work grows with the square of the text length [3]. So a model reads only a limited number of tokens at once — 2,048 for GPT-3 [5], hundreds of thousands for current models. Whatever does not fit, the model does not see.

One token at a time

To produce an answer, a GPT does one thing, over and over: given the text so far, it computes how likely each possible next word is — more precisely the next text fragment, a token. One is drawn, appended, and the whole text goes in again [8]:

Why not always take the most likely token? Because then, as Stephen Wolfram observes, the text tends to become flat and repetitive; a little randomness makes it livelier [8]. The price: the same prompt can give different answers. GPTs are therefore neither transparent — you cannot trace how an output came about — nor deterministic.

For the curious
  • Where tokens come from. The vocabulary is not designed by hand. Byte-pair encoding starts from single characters and keeps merging the most frequent neighbouring pair into a new token [15]. Frequent words end up as one token, rare ones as several pieces. That is also why LLMs are clumsy at counting letters: they never see the letters.
  • Temperature. The model actually outputs a score per token; the probabilities come from them by a softmax, after dividing every score by the temperature. Below 1 the likely tokens get even likelier; above 1 the distribution flattens and rare tokens get a chance. At temperature 0 the most likely token is always taken.
  • Top-k and top-p. Most systems also cut off the long tail before drawing: only the k best tokens, or only the smallest set whose probabilities add up to p (“nucleus sampling”) [16]. That keeps the variety of sampling without the occasional absurd token.

Hallucinations

LLMs are built on a stochastic model. So an LLM does not necessarily give the correct answer, but the most plausible one. As long as the requested information lies within the training data, the most plausible answer is often also the right one; the further outside the training data you go, the more likely it is that the LLM presents a wrong answer very plausibly.

Hallucinations are hard to spot, because they are hard to tell apart from correct statements: they always fit the context of the question and rarely contain obvious errors. The following example shows a mistake any human sees at once — and the model does not. Nothing in the answer reveals its uncertainty.

Reasoning is just as fragile. “Alice has 5 sisters and 3 brothers. How many sisters does a brother of Alice have?” — state-of-the-art models answered this correctly only a fraction of the time [7]. LLMs imitate language very well, but they have no concept of logic of their own. Tools close part of the gap: code interpreters, function calls, APIs. An LLM that uses such tools in a loop is called an agent.

For the curious

Why does a model not simply say “I don’t know”? One answer: training and evaluation reward guessing. In a test that scores right answers and gives nothing for “I don’t know”, a guess is always the better bet — for students in an exam and for language models in a benchmark. Kalai et al. argue that hallucinations follow from exactly this, and that fewer of them need different scoring: wrong answers must cost more than an honest “I don’t know” [17]. The 17 dots add a second cause: the image model and the language model are separate, and the language model does not look at what was actually drawn.

02Basic terms

Talk about AI quickly fills up with words. Here are the ones you need — from the umbrella term down to agents and harnesses.

AI is an umbrella term

“Artificial intelligence” is a very broad and loosely defined term. Besides neural networks, even simple decision trees are often called AI. Machine learning narrows it down to algorithms that learn from data; deep learning to those that use neural networks; generative AI to systems that create new content. Large language models are the innermost circle — and the one this article is about.

Words around the model

Token
A piece of text the model reads and writes: a word, part of a word or a punctuation mark. GPT-3 knows about 50,000 different tokens; only a few thousand of them are whole words [8].
Prompt
Everything the model gets as input: the instructions (system prompt), the conversation so far, attached documents.
Context window
How many tokens the model can take in at once. Whatever does not fit, it does not see.
Temperature
How adventurous the choice of the next token is. At 0 it is always the most likely one; higher values bring variety — and more mistakes.
Few-shot
Examples of questions and answers in the prompt that show the model what is wanted — without training it again.
Fine-tuning
Training an existing model further on one’s own data. Needs good data and hardware, and the result stays fixed until the next training.

Embeddings

Inside, an LLM does not work with words but with vectors — long lists of numbers. These embeddings are learned so that words and texts with similar meaning end up close together, in a kind of meaning space [8]:

That makes semantic search possible: users describe their problem and get the matching content, without having to know which terms to search for.

For the curious
  • How many dimensions? The figure has two; real embeddings have hundreds to thousands — GPT-3 works with 12,288 numbers per token [5]. Nobody chose what each number means; the axes are whatever the training found useful.
  • Close means similar. Closeness is usually measured as the angle between two vectors (cosine similarity), not their distance — a long and a short text on the same topic point the same way.
  • Arithmetic with meaning. Directions in the space can carry meaning. In word embeddings of 2013, the vector of king minus man plus woman landed closest to queen [18].

Retrieval-augmented generation (RAG)

An LLM only knows what was in its training data. To let it answer from your own documents, you do not train it again — you search first and hand it what you found. Combined with semantic search, this is retrieval-augmented generation:

For the curious
  • Before the first question. The documents are cut into chunks of a few paragraphs, each chunk is turned into an embedding, and the embeddings go into a vector index.
  • At every question. The question is embedded the same way; the index returns the nearest chunks; they are pasted into the prompt together with the instruction to answer from them and to name the source. The name and the idea go back to Lewis et al. [20].
  • Where it goes wrong. Mostly in the search, not in the model: chunks cut in the wrong place, a question that uses other words than the documents, a table that loses its structure. Many systems therefore combine semantic search with plain keyword search and let a second model re-rank the hits.

What is an agent?

Agent

An AI agent is a language model that uses tools in a loop to reach a goal — and decides for itself which step comes next.

A chatbot answers a question and stops. An agent gets a goal, plans, acts — reads a file, runs a search, edits code —, looks at the result and decides what to do next, until the goal is reached. Simon Willison puts it in one line: “An LLM agent runs tools in a loop to achieve a goal.” [10]

Anthropic draws the line against workflows: in a workflow, LLMs and tools follow paths a programmer laid down in advance; in an agent, the LLM directs its own process and its use of tools [9]. That makes agents flexible — and harder to predict.

What is a harness?

Harness

A harness is all the software around a language model that turns it into a working agent — everything in the agent except the model itself.

The word comes from the harness of a horse. The horse brings the strength, but only the harness — collar, reins, the cart behind — turns that strength into directed, useful work. A language model on its own can only turn text into text. The harness runs the loop of gathering context, acting, checking the result and going again, and around it provides:

  • instructions — the system prompt and the rules of the project,
  • tools — files, a terminal, a browser, web search,
  • context and memory — what the model gets to see, summarised when the context window fills up,
  • guardrails — permissions, a sandbox, what needs a person’s approval,
  • checks — tests, linters, parsers that tell the model when it went wrong.

Hence the short formula: agent = model + harness [12]. Claude Code, Codex and Cursor are harnesses. Part of the harness comes built in; teams add their own on top — project rules, extra tools, their own checks. Birgitta Böckeler sorts these additions into guides, which steer the agent before it acts, and sensors, which observe afterwards and help it correct itself [11].

For anyone building with AI, this is the practical lesson: much of what makes an agent good or bad sits in the harness, not in the model. ESACA, the project I work on, is such a harness for companies — coding agents inside the company’s own perimeter. And the next chapter shows two harness parts for models: a parser as a sensor, a grammar as a guide.

03LLMs and model-driven engineering

Software engineering is a complex discipline with many hurdles: programming skills, experience in system modelling, domain knowledge and a lot of coordination between the stakeholders of the platform being built. Generative AI can already take over parts of this work and speed development up [4]. Assistants such as GitHub Copilot help programmers write parts of the source code. Far fewer approaches deal with modelling and generating whole systems.

Generative methods can create systems, or parts of them, from textual models: a generator reads a model and produces source code from it. Depending on what the code is for, different modelling languages fit — class diagrams for data structures, sequence diagrams for processes. What models, DSLs and generators are is explained in part 1 of this series.

Language models that write models

Defining good models takes knowledge: of modelling concepts, of the syntax of the modelling language and of the use case. LLMs can help most with the first two. With prompt engineering we can teach an LLM a modelling language [BDMN+24] [NMR24] — combining few-shot learning [5], retrieval-augmented generation [6] and instructions to turn natural-language input into a textual model in the language of our choice.

LLMs tuned for a modelling language can do more than create new models: they can change existing ones, or extract a model from a picture. A model sketched on a whiteboard can be photographed and turned into proper syntax.

Constrained decoding: grammar masking

Even better is to not let invalid models arise at all. An LLM writes one token at a time — so at every step, before a token is chosen, the grammar of the modelling language can filter the candidates. This is grammar masking [NRR24]:

Small open models running locally then produce valid models more than nine times out of ten — instead of between almost never and four times out of ten. The price is runtime. Masking needs access to the token probabilities, which is why it works with open models running on one’s own hardware.

For the curious
  • Why it is a guarantee. A parser afterwards can only reject; the mask decides beforehand. If every chosen token keeps the text a valid beginning of a model, and the model may only stop when the text is complete, the result is syntactically valid by construction — not just likely to be [NRR24] [19].
  • Tokens do not match the grammar. A token can contain half a keyword, or a brace plus a space plus the next name. So the mask cannot simply look up grammar symbols; it checks for every candidate whether its characters can continue the text so far. Doing that fast for tens of thousands of tokens at every step is the engineering part.
  • Syntax, not meaning. The mask ensures the model parses. Whether the classes are the right ones, or whether a referenced class exists at all, still needs checks afterwards — and the model can be pushed into valid but awkward text when it “wanted” something else.
  • Hosted models. Several API providers now offer a narrower form on their side: output that is guaranteed to follow a JSON schema.

From a sentence to an application

Put together with model-driven engineering, this goes all the way: users describe their domain informally, an LLM derives the class diagrams, and a generator such as MontiGem turns them into a complete information system [NMR24] [Net24].

Models help far beyond generating software artefacts. Requirements can be translated from natural language into a formal language a computer can analyse; contradictions and redundancies found there can be translated back into natural language by an LLM. And because a generated model can be analysed and checked, many sources of error are ruled out before a single line of code exists [NKR+25].

In short

AI cannot replace a developer yet; it is best seen as a tool that speeds up the development process. Everything it produces needs checking and validation — it cannot be used blindly. That checking belongs in the harness, and where AI meets models it becomes possible: the model is the place where language turns into something a machine can verify.
