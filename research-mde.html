02Model-Driven Software Engineering

article · 2026

Software from models: what DSLs, models and generators are — and how one class diagram becomes a running web application.

Series · part 1: Model-driven SEpart 2: AI-driven SEpart 3: Digital twinspart 4: Evolutionary algorithms

Models and languagesFrom model to codeMontiGem, CD2GUI and beyond

You have modelled before — maybe without calling it that. A spreadsheet formula describes a calculation that the spreadsheet carries out. An SQL CREATE TABLE describes data that the database then stores. A JSON schema describes a form that a library then draws. Each time you wrote down what you want in a small, specialised language, and a machine turned it into behaviour. If you have used Power Apps, a form builder or an OpenAPI code generator, you have used model-driven tools.

“A model is an abstraction of an original made and used for a purpose.”

after Herbert Stachowiak, 1973 · [DGM+21]

Model-driven software engineering makes this the method: the important decisions about a system are written down as models, and generators turn the models into code — again and again, whenever the models change. This article explains the three building blocks — models, the languages they are written in, and the generators that read them — and then shows how far they carry: with MontiGem and CD2GUI, a single class diagram becomes a running web application with database, server and pages.

Who does what? Domain experts describe or review the models; modellers add page models; programmers add the special logic that no model covers; and tool builders make the generators. You will meet all four.

01Models and languages

Before anything can be generated, something has to be written down — and written down in a way a machine can read. This chapter is about the what: models, and the languages they are written in.

What is a model?

A model depicts something, it leaves things out, and it serves a purpose. Herbert Stachowiak named these three features in 1973 [2] — mapping, reduction and pragmatism — and they still are the best test for any model. A metro map is a model of a city: every dot stands for a real station (mapping), streets and hills are gone (reduction), and what remains is exactly what you need to get across town (purpose). A hiking map of the same city keeps the hills and drops the stations. Neither is “more correct” — each is good for something else.

So the useful question about a model is never “is it complete?” but “what is it for?”. In software, the original can be something that exists — a business process, an existing database — or something that is still to be built: the model of a system describes it before it is there.

Model

A model describes some original, real system or entity that exists or is intended to exist in the future. A model is an abstraction of the original. A model has a purpose with respect to the original. [1]

For the curious
  • Descriptive or prescriptive. A model can describe what is (an analysis of today’s process) or prescribe what shall be (the design of tomorrow’s system). Generators work with prescriptive models.
  • Explicit or programmed. A text or diagram model is explicit; a model can also be “an implicit model that is encoded in an executable program” [1] — every program contains one.
  • Model-based or model-driven. In model-based development, models support some activities; in model-driven development, “models also drive and guide the development process, and thus, models are the primary engineering artifacts” [1].
  • Many models. “A model always represents only a limited scope of aspects of the real world. Thus a set of multiple models is used” [GHK+20].

Reading a class diagram in 60 seconds

Most of this article works with one kind of model: the class diagram. It describes the kinds of things in a domain and how they relate. A class is a kind of thing (Account, Person); an attribute is a field every such thing has (a name, a balance). A line between two classes means one knows the other; the numbers at its ends say how many — 1 exactly one, * any number. A hollow triangle means is a. That is enough to read the running example of this article: an accountant at a bank manages several accounts.

The same model can be written as text. CD4A is MontiCore’s textual language for class diagrams [9]; the papers on MontiGem use exactly this example [GMN+20]:

classdiagram Example {
  class Account { String name; int balance; }
  class Person { String name; }
  class Accountant extends Person { String bank; }
  association [1] Accountant -> (account) Account [*];
}

Languages for models: DSL vs. general-purpose

Java, Python or C# can express any program — they are general-purpose languages. A domain-specific language (DSL) does the opposite: it is made for one domain and can say little else, but says it briefly and in the domain’s own terms. You already know several: SQL for data, HTML for documents, CSS for layout, spreadsheet formulas for calculations, regular expressions for text patterns [4]. A DSL “trades some expressiveness of GPLs in order to allow for more concise models” [4] — and it helps exactly the people this article is also written for: “Non-ICT experts benefit from DSLs by being able to transfer already familiar language concepts” [4].

Real systems are described by several small languages, one per aspect: one for the data, one for the pages, one for the rules, one for who may see what. Each stays simple because it does one job — and they fit together because they refer to the same names.

DSL

A domain-specific language (DSL) is a software language specialized for a particular application domain. [1]

For the curious
  • Internal or external. An internal DSL lives inside a host language (a fluent Java API); an external DSL has its own syntax and its own parser [11]. The languages in this article are external.
  • Text or graphics. Experts are faster in text, “not distracted by ‘pushing boxes around’” [8]. Yet the end users in one project preferred the graphical class diagram once it had more than 120 classes [BGK+24]. Good tools offer both views of one model.
  • What a language consists of. Its syntax (how models look), its semantics (what they mean) and its pragmatics (how to use them for their purpose) [1].

The picture is not the model

Is the model the text, or the diagram? Neither. Both are notations — the language calls them concrete syntaxes — for one underlying structure. A tool reads the text with a parser and builds that structure, the abstract syntax tree (AST); a diagram editor draws the same tree as boxes and lines. This is why a generator never cares whether you typed or drew.

And it is why checking happens in steps. First: is the text readable at all — does the parser accept it? Second: are all names known — does every Account that is mentioned exist? Third: are the rules kept — for example, no two attributes with the same name? The grammar only answers the first question. The rest are context conditions, “boolean predicates constraining the set of models to the subset of well-formed models” [1], written by hand against the AST [8].

Names are also how models refer to each other. A page model says Account and means the class in the data model — through the symbol table, an index of all named elements, even across files and languages. No copies, so nothing can drift apart [GMN+20]. And grammars can do more than check: they can also constrain what an LLM writes, token by token — see grammar masking in part 2.

One level up: languages for languages

A model conforms to its language, and the language is defined by a grammar (as in MontiCore) or by a metamodel: “A metamodel is a model describing the abstract syntax of a language” [1]. MontiCore derives such a description from every grammar internally, as a class diagram [8]. Separate from this conforms to is the instance of of objects and classes: the object bob : Accountant is an instance of the class Accountant; the class diagram itself conforms to CD4A. And what a model means is a third question: its semantics, a mapping into a semantic domain [1].

02From model to code

A model on its own is documentation. It starts to drive development when a program reads it and produces something from it: code, other models, tests, documentation. That program is a generator.

What a generator does

Start with the problem. In a typical business application, the same data structure turns up again and again: as a database table, as a server class, as a transfer object, as a model in the browser, as a form. Writing these by hand is tedious and error-prone — and it is schematic: knowing the data structure, you could almost type the rest blindfolded. That is exactly what can be generated [GMN+20]. “Code generation is the process of translating a source model into artifacts of an executable language” [1].

Most generators work like mail merge. A template is the target code with holes in it — “pieces of code with holes in it, which will be filled upon generation” [8]; the model fills the holes. In FreeMarker, the template engine MontiCore uses, it looks like this (adapted from the handbook [8]):

package ${ast.packageName};
<#assign cname = ast.name>
public class ${cname}Factory {
  public static ${cname} create() {…}
}

Filled with a class Person, it yields public class PersonFactory {…}. The model carries the domain, the templates carry the technology [8] — swap the templates, and the same model produces code for another platform.

A real generator does more than fill templates. It reads the model and checks it, transforms it into a structure closer to the target — adding, for example, an id nobody modelled — and only then generates. Some generators produce not code but another model: a model-to-model (M2M) transformation, as opposed to model-to-text (M2T). CD2GUI, which you will meet in chapter 03, is one. And a generator adds things that were never in the model at all — login, persistence wiring — on top of a hand-built runtime environment, the ready-made part the generated code plugs into [5].

If you have generated a TypeScript client from an OpenAPI specification, you have used a generator. Those are usually run once. The generators in this article are run again and again — which raises the question of the next section.

Generator

Code generation is the process of translating a source model into artifacts of an executable language. A generator consists of a transformation engine and a runtime environment. [1] [5]

Model transformation

A model transformation applies to one or more source models and transforms them into one or more target models. [1]

For the curious
  • Why an intermediate AST. “If the conceptual distance, however, becomes too large, it is advisable to transform the AST of the input language to an AST that is better suited for the output language” [8].
  • One model, several meanings. The same model can be mapped differently: a state Off might become an enum constant, an integer, a subclass or a method [9]. So the semantic variant has to be clarified before a generator is built [5].
  • Configurable generators. Templates can be replaced at hook points [8], and generators should be able to leave out what a project does not use — unused generated endpoints are a security issue [BGK+24].

Generated and hand-written code

Complete generation is rare: real systems mix generated and hand-written code — the business rule no model covers, the special screen, the connection to an old system [10]. The rule that makes this work is simple: never edit generated code. “A one-shot generation is not helpful, because it does not assist any form of evolution … So, it is best to not manually touch generated code” [8]; changes there “would be overwritten in the next generation-cycle” [GMN+20].

Instead, hand-written code builds on the generated code. MontiCore and MontiGem use the TOP mechanism for this: “The handcoded class Cls replaces the generated class Cls, which now becomes generated as ClsTOP” [8] — and the hand-written class extends it. Everything else in the system keeps using the name Cls and gets the hand-written version.

The price is small but real: the generator has to look for hand-written files, so after adding or removing one you regenerate once [8]. And the trick has a limit — HTML has no inheritance, and page models are trees, not classes; TOP “is not applicable to the GUI-model, due to its nested tree structure” [GMN+20]. How pages are customised instead is shown under CD2GUI. The lesson from five projects is plain: “a code generator has to support hand-written code extensions” [BGK+24]. The MontiGem page shows the AccountTOP example in full.

For the curious
  • Other mechanisms. The classic generation gap uses a generated base class and a hand-written subclass with a different name; others use delegation, partial classes or “protected regions” inside generated files — the last are fragile [10].
  • Separate folders. Hand-written and generated code live in separate directory trees; generated code does not belong under version control [8].
  • Not round-trip engineering. Code is never fed back into the model: the model stays the source, the code is always derived.

When the model changes

Regenerating is safe for the code. But a running system also has data, and that data was stored in the shape of the old model. “Changes in the application create a need for (a) system migration and optional (b) data migration” [DGM+21] — a new column needs a default, a split class needs its rows split. Experience from practice: additions to models are cheaper than changes to existing parts [DGM+21]. For agile work, generators also have to be “incremental, compositional and therefore quick” [5], and they can generate simple tests from the page models along the way [DGM+21].

Research goes one step further: comparing two versions of a model not line by line but by meaning — what can the new model express that the old one could not? That is what my work on the evolution of domain models looks at [BNR+25].

03MontiGem, CD2GUI and beyond

Now the pieces come together: a generator framework that turns class diagrams into complete web applications, a transformation that derives the pages, the language workbench underneath — and what all of this has to do with low-code and AI.

Why information systems can be generated

Think of the software that administrations run on: finances, staff, inventory, projects. Lists, forms and detail pages over a central database — and at their core always the same four operations: create, read, update and delete, CRUD for short [GMN+20]. Such information systems are big, but their structure repeats with every class of the data model. That makes them the ideal target for a generator.

MontiGem — the MontiCore-based Generator for Enterprise Management — is such a generator. The class diagram is “the only mandatory model” [GMN+20]; page models, rules and access tags can be added. In three steps — read, transform, generate [6] — it produces a three-tier web application: a database with its access layer, a Java server, and an Angular/TypeScript front end [CMNR24], running on a hand-built runtime environment. Because all tiers come from the same model, they are “consistent-by-design” [GHK+20]. Even an empty data model already yields an application — with only a login page [Net24].

MontiGem has a history: its predecessor was called WebDEx [ANV+18], and the generator itself was first built inside the MaCoCo project and extracted into a framework of its own after about three years [BGK+24]. More on the MontiGem project page.

Describing pages: the GUI-DSL

Pages get their own language. A GUI-DSL model describes one page as a tree: a page holds cards, a card has a head and a body, the body holds tables, buttons, labels [GMNR21]. And it refers into the class diagram by name — the symbol table at work. This is a complete page model [BGK+24]:

webpage Staff(all Person p) {
  card {
    head { label "Staff Overview" }
    body {
      datatable { rows <p {
        column "Name", name
        column "Birthday", birthday
}}}}}

all Person p loads all persons; rows <p makes one table row per person; column "Name", name shows the attribute name from the class diagram. Data, page and rules, each in its own language, end up on one screen:

One piece of advice from practice: do not bury large amounts of hand-written HTML inside page models — they become as hard to read as the HTML itself; keep highly specific parts entirely hand-written [BGK+24]. CD2GUI: from a class diagram to an application

Page models still have to be written. CD2GUI removes even that step: it “takes only one class diagram as input and generates data and GUI models which are further processed by the MontiGem generator framework into a running application” [6]. It is a model-to-model transformation: out of the class diagram come page models, and MontiGem turns them into code as if someone had written them by hand. For every class it derives an overview page (all objects in a table) and a details page (one object with its attributes and associations), plus one dashboard for all classes; interfaces and enums get no pages of their own [GMN+20] [Net24].

And when the client wants something else — no accounts table on this page, two buttons instead? Not in the generated HTML: in a small hand-written delta model with operations such as remove, replace, add_to, add_before and add_after, applied to the generated page tree before code is generated [GMN+20]. In practice: MaCoCo and four other domains

MontiGem did not start on a whiteboard but in a running system. MaCoCo, the management cockpit RWTH chairs use for their finances, staff and projects, began as a hand-written application; generation was added to it one aspect at a time, following a method of 16 activities [DGM+21].

A snapshot from March 2022 [GLM+24]:

74.59 %of the code generated
500,573generated lines
73 · 74domain classes · GUI models
1,403users at 188 chairs

The same generator has been used in four more domains [BGK+24]: tool tracking for craftsmen with Ford, energy management of buildings, the privacy policies of wearables (InviDas), and the engineering of wind turbines (ADD). What did five projects teach?

GOOD FIT
  • data-centric applications built around CRUD [GMN+20]
  • early prototypes that stakeholders can click through — they show problems with requirements and data structures “at a very early stage” [BGK+24]
  • teams with examples and documentation: learning to model “does not take much time, even for untrained students” [BGK+24]
POOR FIT
  • specific customer UI requirements — generated pages were great for prototypes, “not usable for specific customer requirements” [BGK+24]
  • non-standard user experience, where native apps did better [BGK+24]
  • teams without the expertise: MDE “requires a high level of expertise”, and the result is limited by the quality of the data model [BGK+24] [GMN+20]

Under the hood: MontiCore

Where do the languages CD4A, GUI-DSL and OCL/P come from, with their parsers, symbol tables and checks? From MontiCore, “a language workbench for the efficient development of domain-specific languages”, developed at the RWTH chair of Software Engineering since 2004 [7]. MontiCore is a generator whose products are generators themselves — a meta-tool [8]. From one grammar it generates a language tool’s front end: parser, AST classes, symbol-table infrastructure, a framework for context conditions, visitors and a template-based generator framework [8]; the language engineer adds the rules, the tool builder the transformations and templates.

Its strength is composition: languages are built from languages. The GUI-DSL refers to CD4A through symbols, OCL/P embeds an expression language, CD4Code extends CD4A with methods [8] [9]. That is how MontiGem’s family of languages could grow without being rewritten. The handbook is free, the languages CD4A and OCL are on GitHub — and my assistant answers questions on the handbook:

Where this leads: low-code and AI

Low-code platforms promise applications without programming. Seen from MDE, they are a familiar recipe: “Low Code == a Modeling Language plus Domain-Specific Functionality plus a Platform and/or a Software Creating/Generating Tool” — and “there is always a LCML involved, even if the language is not defined or even mentioned explicitly” [12]. Behind the wizards sits a modelling language. Platforms differ in what they do with the models: some generate code, as MontiGem does; others combine generation with interpreting the models at run time [CMNR24]. Both are model-driven.

Will business people now write their software themselves? The same was promised for COBOL [11], and low-code languages tend to grow back into fuller languages over time [12]. The realistic role for citizen developers is that of co-authors of models — which is what this article is meant to prepare for.

And then there is AI. Writing the model is the step that still takes expertise — and it is the one an LLM can help with: describe the domain in a sentence, and the LLM writes the class diagram; CD2GUI and MontiGem do the rest, deterministically [NMR24]. Without context, GPT-4 wrote no valid CD4A model in 20 tries; once the conversation had explained the language with examples, 99 of 100 were valid [NMR24].

How an LLM works, how it learns a modelling language and how a grammar keeps it from writing invalid models is the subject of part 2 of this series: AI-driven software engineering — continue with language models that write models. All my modelling assistants in one place:

In short

  • A model is a purposeful simplification of an original: ask what it is for, not whether it is complete.
  • The picture is not the model: behind text and diagram sits a structure tools can check — and “it parses” is not “it is correct”.
  • A DSL gives up generality to get close to one domain; you already use several.
  • A generator is a translator that carries architectural decisions: one model line becomes consistent code in every tier.
  • Generated and hand-written code are kept apart, so you can regenerate at any time — the value lies in repeated generation, not in a one-shot scaffold.
  • CD2GUI and MontiGem turn one class diagram into a running prototype that grows into a full-size system without being thrown away — great for prototypes, limited for very specific interfaces.
  • Low-code is MDE with a platform and a friendlier surface; AI fits in front of it: the LLM writes only the model, and a deterministic, checkable generator does the rest.
