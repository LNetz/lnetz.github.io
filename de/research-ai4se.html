    Wie erzeugt ein Sprachmodell Text, warum liegt es manchmal selbstsicher falsch — und wie wird seine Ausgabe verlässlich genug, dass Software darauf aufbauen kann? Von Tokens über Agenten bis zu Sprachmodellen, die Modelle schreiben.

    Bitten Sie einen Chatbot um das Datenmodell einer kleinen Bibliotheks-App — Bücher, Mitglieder, Ausleihen — als JSON. Was zurückkommt, sieht auf den ersten Blick richtig aus. Gibt man es einem Programm, scheitert es manchmal: Eine schließende Klammer fehlt, ein Schlüssel hat seine Anführungszeichen verloren, oder vor dem JSON steht ein freundlicher Satz.

    AI4SE umfasst auch Anforderungsarbeit, Tests, Reviews und Fehlersuche. Dieser Artikel konzentriert sich auf LLM-gestützte Modellierung und modellgetriebene Generierung und beantwortet dazu drei Fragen. Wie erzeugt ein Sprachmodell solchen Text? Warum liegt es manchmal falsch — und klingt dabei genauso sicher? Und wie machen wir seine Ausgabe verlässlich richtig, sodass ein Programm, etwa die Generatoren aus Teil 1, darauf aufbauen kann?

    01Was ein LLM tut

    Ein LLM — ein großes Sprachmodell (Large Language Model) — hat eine Sache außerordentlich gut gelernt: einen Text fortzusetzen. Antworten, übersetzen, Code schreiben — alles folgt daraus. Dieses Kapitel geht von außen nach innen: erst, was man im Chatfenster sieht, dann, was darin passiert.

    Token für Token

    Um zu antworten, macht ein LLM immer wieder nur eines: Zum bisherigen Text berechnet es, wie wahrscheinlich jedes mögliche nächste Textstück ist. So ein Stück heißt Token — ein Wort, ein Wortteil oder ein Satzzeichen. Ein Token wird gezogen, angehängt, und die Erzeugung läuft mit diesem Kontext weiter (meist mit zwischengespeicherten Attention-Keys und -Values) [1]:

    Warum nicht immer das wahrscheinlichste Token? Weil der Text dann eher flach und repetitiv wird; ein wenig Zufall macht ihn lebendiger. Der Preis: Derselbe Prompt kann unterschiedliche Antworten liefern, und nichts in der Ausgabe verrät, warum ein Token gewählt wurde. Die Temperatur regelt, wie viel Zufall im Spiel ist — dreht man sie hoch, wächst die Vielfalt, erst in der Formulierung, dann in den Fakten.

    Für NeugierigeTokens und Ziehen
    • Woher die Tokens kommen. Das Vokabular entwirft niemand von Hand. Byte-Pair-Encoding beginnt je nach Tokenizer mit Zeichen- oder Byte-Einheiten und verschmilzt immer wieder das häufigste benachbarte Paar zu einem neuen Token [2]. Häufige Wörter werden ein Token, seltene mehrere Stücke. Deshalb tun sich LLMs auch schwer, Buchstaben zu zählen: Variable Tokengrenzen machen das zeichenweise Zählen weniger direkt.
    • Temperatur. Eigentlich gibt das Modell pro Token einen Wert aus; die Wahrscheinlichkeiten entstehen daraus per Softmax, nachdem jeder Wert durch die Temperatur geteilt wurde. Unter 1 werden die wahrscheinlichen Tokens noch wahrscheinlicher; über 1 wird die Verteilung flacher, und seltene Tokens bekommen eine Chance. Bei Temperatur 0 wird immer das wahrscheinlichste Token genommen.
    • Top-k und Top-p. Die meisten Systeme schneiden vor dem Ziehen außerdem den langen Schwanz ab: nur die k besten Tokens, oder nur die kleinste Menge, deren Wahrscheinlichkeiten zusammen p ergeben („Nucleus Sampling“) [3]. So bleibt die Vielfalt des Ziehens, ohne gelegentliches absurdes Token. Die Demo oben zieht nur unter den gezeigten Kandidaten.

    Aus Wörtern werden Zahlen: Embeddings

    Im Inneren arbeitet das Modell mit Zahlen, nicht mit Wörtern. Jedes Token wird zu einem Vektor — einer langen Zahlenliste —, dem Embedding. Die folgende zweidimensionale Spielzeugdarstellung ist von klassischen statischen Wort-Embeddings inspiriert, kein gemessener GPT-Tokenraum:

    Tokenrepräsentationen im Transformer werden über die Schichten kontextabhängig. Semantische Suche nutzt meist ein separates Embedding-Modell für ganze Fragen und Textabschnitte: Ein Satz über einen fröhlichen Hund und einer über einen verspielten Vierbeiner landen nah beieinander, obwohl sie kein Wort teilen. Das ermöglicht semantische Suche — eine Stelle nach ihrer Bedeutung finden, nicht nach ihren genauen Wörtern. Kapitel 02 baut darauf auf.

    Für NeugierigeDimensionen und Abstand
    • Wie viele Dimensionen? Die Abbildung hat zwei; echte Embeddings haben Hunderte bis Tausende — GPT-3 arbeitet mit 12.288 Zahlen pro Token [4]. Niemand hat festgelegt, was jede Zahl bedeutet; die Achsen sind, was das Training nützlich fand.
    • Nah heißt ähnlich. Nähe misst man meist als Winkel zwischen zwei Vektoren (Kosinus-Ähnlichkeit), nicht als Abstand — ein langer und ein kurzer Text zum selben Thema zeigen in dieselbe Richtung.
    • Rechnen mit Bedeutung. In Wort-Embeddings von 2013 lag der Vektor king minus man plus woman am nächsten an queen [5].

    Im Inneren: ein neuronales Netz

    Was aus diesen Zahlen das nächste Token macht, ist ein neuronales Netz. Die Idee ist älter, als sie aussieht — das erste, das Perzeptron, stammt von 1958 [6] — und am einfachsten an einem Bild zu sehen: Ist das ein Hund oder eine Katze?

    Das Netz sieht keinen Hund, nur Pixelwerte, eine Zahl pro Eingabe. Jede Verbindung hat ein Gewicht: eine Zahl, die sagt, wie viel eine Eingabe zählt. In diesem Spielzeugnetz nutzen die versteckten Neuronen ReLU: Negative gewichtete Summen werden null. Softmax wandelt die zwei Ausgabewerte in Wahrscheinlichkeiten um.

    Training passt die Gewichte über viele Beispiele an, bis die richtige Ausgabe gewinnt. Zum Vergleich: Der Fadenwurm C. elegans kommt mit 302 Neuronen aus; GPT-3 hat 175 Milliarden Gewichte (Parameter und biologische Neuronen sind verschiedene Größen) [4].

    Für NeugierigeWie die Gewichte gelernt werden
    • Wie sich die Gewichte bewegen. Nach jedem Beispiel vergleicht das Netz seine Ausgabe mit der richtigen Antwort. Backpropagation rechnet Schicht für Schicht von hinten aus, wie viel jedes Gewicht zum Fehler beigetragen hat [7]; dann wird jedes Gewicht ein winziges Stück in die Richtung verschoben, die den Fehler kleiner macht (Gradientenabstieg). Das Ganze milliardenfach.
    • Pre-Training. Ein LLM braucht keine beschrifteten Bilder: Die richtige Antwort ist einfach das nächste Token eines echten Textes. Das ermöglicht Lernen aus großen Sammlungen unbeschrifteter Texte.
    • Vom Textfortsetzer zum Assistenten. Ein vortrainiertes Modell setzt nur Text fort. Mögliche Nachtrainingsschritte sind Instruction Tuning und Präferenzoptimierung wie RLHF: Menschen bewerten Antworten, ein Belohnungsmodell lernt diese Vorlieben, und das LLM wird darauf hin angepasst (RLHF). In der InstructGPT-Studie zogen Menschen die Antworten eines so angepassten Modells mit 1,3 Milliarden Gewichten denen von GPT-3 mit 175 Milliarden vor [8].

    Was den Durchbruch brachte: Attention und Größe

    Welche früheren Wörter zählen für das nächste? 2017 machte eine neue Architektur, der Transformer, diese Frage zu ihrem Kern [9]: Jedes Token darf auf jedes frühere Token schauen und abwägen, wie wichtig es ist. Das heißt Attention. Damit löst ein Modell Bezüge wie diesen auf, bei dem ein einziges Wort entscheidet, was „er“ meint:

    Für NeugierigeIm Inneren des Transformers
    • Was Attention berechnet. Jedes Token wird in drei Vektoren übersetzt: eine Query (wonach suche ich?), einen Key (was biete ich an?) und einen Value (was gebe ich weiter?). Ein Token vergleicht seine Query mit den Keys aller früheren Tokens; je besser sie passen, desto mehr von deren Value nimmt es auf. Die Spielzeugdarstellung zeigt für „groß“ eine solche rückwärts gerichtete Beziehung, keine gemessene Erklärung.
    • Viele Köpfe, viele Schichten. Mehrere solcher Attention-„Köpfe“ arbeiten nebeneinander, jeder kann eine andere Art von Bezug lernen, und die Schichten sind gestapelt — 96 bei GPT-3, jede 12.288 Zahlen breit.
    • Das Kontextfenster. Volle Standard-Attention über eine Eingabesequenz hat quadratischen Aufwand. Decoding mit Cache und sparse oder gleitende Attention haben andere Kosten. Kontextlimits hängen auch von Training, Architektur und Betrieb ab — 2.048 bei GPT-3, Hunderttausende bei aktuellen Modellen. Was nicht hineinpasst, sieht das Modell nicht.

    Plausibel, nicht wahr: Halluzinationen

    Ein LLM wählt die plausibelste Fortsetzung, nicht die wahre. Modelle können über Trainingsbeispiele hinaus verallgemeinern und auch bei vertrauten Fakten scheitern. Flüssige Formulierungen und Abdeckung in Trainingsdaten belegen keine faktische Richtigkeit.

    Für Entwickler ist der am besten belegte Fall Code, der Pakete importiert, die es nicht gibt. Eine Studie erzeugte mit 16 Modellen 576.000 Code-Beispiele in Python und JavaScript: Im Schnitt existierten mindestens 5,2 % der Pakete, auf die kommerzielle Modelle verwiesen, gar nicht, bei Open-Source-Modellen 21,7 % — 205.474 verschiedene erfundene Namen [11]. Jeder kann so einen Namen in einem Paketverzeichnis registrieren und Schadcode dahinterlegen.

    Genauso brüchig ist das Schlussfolgern. „Alice hat 5 Schwestern und 3 Brüder. Wie viele Schwestern hat ein Bruder von Alice?“ — die besten Modelle von 2024 lagen hier oft falsch [12]. Werkzeuge schließen einen Teil der Lücke: ein Code-Interpreter, ein Blick ins Paketverzeichnis, ein Testlauf. Ein LLM, das Werkzeuge in einer Schleife einsetzt, ist ein Agent.

    Für NeugierigeWarum Modelle raten

    Warum sagt ein Modell nicht einfach „Weiß ich nicht“? Eine Antwort: Training und Bewertung belohnen das Raten. In einem Test, der richtige Antworten zählt und für „Weiß ich nicht“ nichts gibt, ist Raten immer die bessere Wette — für Studierende in der Klausur wie für Sprachmodelle im Benchmark. Kalai et al. argumentieren, dass Halluzinationen genau daraus folgen und dass es für weniger davon eine andere Bewertung braucht: Falsche Antworten müssen mehr kosten als ein ehrliches „Weiß ich nicht“ [13].

    02Was um das Modell herum entsteht

    Ein Modell allein verwandelt Text in Text. Das meiste, was KI in der Praxis nützlich macht, entsteht drumherum: Suche, Werkzeuge, Schleifen und Prüfungen. Zuerst die Begriffe.

    Die Begriffe

    I propose to consider the question, “Can machines think?”

    Alan M. Turing · Computing Machinery and Intelligence, 1950

    Die Frage ist älter als Computer, wie wir sie kennen [14], und „Künstliche Intelligenz“ ist ein breiter, unscharf definierter Begriff geblieben: Auch einfache Entscheidungsbäume werden gern KI genannt. Machine Learning grenzt das auf Algorithmen ein, die aus Daten lernen; Deep Learning auf solche mit neuronalen Netzen; generative KI auf Systeme, die neue Inhalte erzeugen. Generative KI beschreibt eine Fähigkeit, auch mit Verfahren außerhalb von Deep Learning. LLMs sind eine wichtige Klasse generativer Deep-Learning-Modelle; ChatGPT und Copilot sind Produkte aus Modellen und Software:

    Und vier Begriffe, die beim Arbeiten mit LLMs immer wieder fallen:

    Prompt
    Alles, was das Modell als Eingabe bekommt: die Anweisungen (System-Prompt), das bisherige Gespräch, angehängte Dokumente.
    Kontextfenster
    Wie viele Tokens das Modell auf einmal aufnehmen kann. Was nicht hineinpasst, sieht es nicht.
    Few-shot
    Beispiele für Fragen und Antworten im Prompt, die dem Modell zeigen, was gewünscht ist — ohne es neu zu trainieren.
    Fine-tuning
    Ein bestehendes Modell auf eigenen Daten weitertrainieren. Braucht gute Daten und Hardware, und das Ergebnis steht fest bis zum nächsten Training.

    RAG: eigene Dokumente mitgeben

    Ein LLM kann gelernte Muster ebenso wie Informationen im Kontext oder aus Werkzeugen nutzen. Damit es aus eigenen Dokumenten antwortet, trainiert man es nicht neu — man sucht zuerst und gibt ihm, was man gefunden hat. Zusammen mit der semantischen Suche aus Kapitel 01 ergibt das Retrieval-Augmented Generation (RAG) [15]:

    Nutzer können ihr Problem in eigenen Worten beschreiben und finden trotzdem die passende Stelle. SE-Chatty, ein Chatbot zu Vorlesungsmaterial, arbeitet so.

    Für NeugierigeAbschnitte, Index, Neusortierung
    • Vor der ersten Frage. Die Dokumente werden in Abschnitte von ein paar Absätzen zerlegt, jeder Abschnitt wird in ein Embedding übersetzt, und die Embeddings kommen in einen Vektorindex.
    • Bei jeder Frage. Die Frage wird genauso eingebettet; der Index liefert die nächstgelegenen Abschnitte; sie werden in den Prompt kopiert, zusammen mit der Frage und der Anweisung, daraus zu antworten und die Quelle zu nennen.
    • Wo es schiefgeht. Suche und Generierung können scheitern. Das Modell kann relevante Belege ignorieren oder Quellen erfinden; Suchprobleme entstehen durch Abschnitte an der falschen Stelle geschnitten, eine Frage mit anderen Wörtern als die Dokumente, eine Tabelle, die ihre Struktur verliert. Viele Systeme kombinieren deshalb semantische Suche mit einfacher Stichwortsuche und lassen ein zweites Modell die Treffer neu sortieren.

    Agenten: Werkzeuge in einer Schleife

    Agent

    Ein KI-Agent ist ein System, in dem ein Sprachmodell den Einsatz von Werkzeugen in einer Schleife steuert, um ein Ziel zu erreichen, und seine nächsten Schritte anhand der beobachteten Ergebnisse wählt.

    Auch Chatbots können Werkzeuge nutzen. Hier bezeichnet Agent ein zielgerichtetes System, dessen LLM die nächsten Schritte wählt. Ein Agent bekommt ein Ziel, handelt — liest eine Datei, führt die Tests aus, ändert Code —, betrachtet das Ergebnis und entscheidet, was als Nächstes zu tun ist, bis das Ziel erreicht ist. Simon Willison fasst das in einem Satz: „An LLM agent runs tools in a loop to achieve a goal.“ [16]

    Anthropic grenzt Agenten von Workflows ab: Im Workflow folgen LLMs und Werkzeuge Pfaden, die ein Programmierer vorher festgelegt hat; im Agenten steuert das LLM seinen Ablauf und seinen Werkzeuggebrauch selbst [17]. Das macht Agenten flexibel — und schwerer vorherzusagen.

    Harness: den Agenten betreiben

    Harness

    Ein Agent-Harness ist die Software samt Konfiguration, die die Schleife um ein Modell betreibt: Kontext zusammenstellen, das Modell aufrufen, erlaubte Werkzeugaufrufe ausführen und Ergebnisse in den nächsten Schritt zurückführen.

    Warum ein eigener Begriff? Ein Modell kann einen Aufruf zum Ausführen eines Tests erzeugen; etwas anderes muss ihn tatsächlich ausführen, das Ergebnis festhalten und das Modell erneut aufrufen. Diese Software hat eigene Entwurfsentscheidungen und Fehlerquellen. Änderungen daran können das Verhalten des Agenten verändern, ohne die Modellgewichte anzutasten. Cloudflare stellt diese Ausführungsschleife ins Zentrum seiner Definition [18].

    Modell, Harness, Agent. Das Modell ist die gelernte Komponente: Es erzeugt aus Kontext eine Ausgabe, die Werkzeugaufrufe enthalten kann. Der Harness verwaltet den Ablauf: Kontext und Zustand, Werkzeugausführung, Rechte, Fortsetzung und Abbruch. Der Agent ist das daraus entstehende zielgerichtete System, in dem das Modell die nächsten Schritte wählt. Das Modell schlägt vor, was zu tun ist; der Harness bestimmt, was ausgeführt werden darf, und führt es aus.

    Ein Durchlauf: einen fehlschlagenden Test reparieren. Der Harness stellt Aufgabe, Projektanweisungen und verfügbare Werkzeuge bereit. Das Modell fordert einen Testlauf an. Der Harness prüft die Berechtigung, ruft den Test-Runner auf und gibt dessen Ausgabe zurück. Das Modell nutzt diese Ausgabe, um eine Änderung oder einen weiteren Test vorzuschlagen. Der Harness wiederholt den Ablauf oder beendet ihn bei einer abschließenden Antwort, einem Limit oder einer Rückfrage an den Menschen. Ein Werkzeugaufruf ist eine Anforderung, noch keine ausgeführte Handlung.

    Wo verläuft die Grenze? Hier umfasst der Harness die Werkzeugadapter und ihre Aufrufregeln; Test-Runner, Repository und externe Dienste sind die angebundenen Werkzeuge und die Umgebung. Eine AGENTS.md-Datei konfiguriert den Harness, wenn sie als Projektanweisung geladen wird. Eine Quelldatei, die zur Fehlersuche gelesen wird, ist Aufgabendaten. Ein Test liefert Feedback, wenn der Harness ihn ausführt und das Ergebnis zurückgibt. Ein Prompt allein stellt keine Ausführungsschleife bereit; ein SDK oder Framework liefert einen Harness nur insoweit, wie es diese Schleife implementiert.

    Für NeugierigeEin Begriff, verschiedene Grenzen

    Es gibt keine allgemein vereinbarte Grenze. Trivedy verwendet die breite Kurzform Agent = Modell + Harness, einschließlich mitgelieferter Infrastruktur [19]. Anthropics Sicherheitsbetrachtung trennt Modell, Harness, Werkzeuge und Umgebung [20]. Dieser Artikel zieht eine betriebliche Grenze: Der Harness steuert den Ablauf und bindet Werkzeuge und Umgebung an. Das sind Zuständigkeiten, nicht zwingend getrennte Prozesse oder Produkte. Ein Coding-Produkt kann alles bündeln.

    Auch braucht nicht jeder Agent jede Harness-Funktion. Dauerhafter Speicher, Kontextkomprimierung, Subagenten und Wiederanlauf sind Erweiterungen, keine Definitionsmerkmale. Anthropics Beispiel für lang laufende Agenten zeigt, weshalb die Fortsetzung über Kontextfenster hinweg gezielte Unterstützung braucht [21]. Ein fester Workflow kann dieselbe Technik nutzen; zum Agenten wird das System hier dadurch, dass das Modell die nächsten Schritte steuert.

    Warum das praktisch zählt. Dasselbe Modell kann sich mit verschiedenen Harnesses unterschiedlich verhalten: Es sieht anderen Kontext, hat andere Werkzeuge und erhält anderes Feedback. Teams können den eingebauten Harness durch Projektregeln und Prüfungen ergänzen. Böckeler nennt diese Guides vor einer Handlung und Sensoren danach [22]. Anweisungen bitten das Modell um ein Verhalten; Rechte und Isolation begrenzen, was ausgeführt werden kann. Abgerufene Inhalte bleiben Aufgabendaten, und eine bestandene Syntaxprüfung belegt weder Sicherheit noch Korrektheit.

    ESACA, das Projekt, an dem ich arbeite, bringt Coding-Agenten in die unternehmenseigene Infrastruktur. Das nächste Kapitel betrachtet zwei konkrete Wege, Modellausgaben zu lenken und zu prüfen: eine Grammatik als Guide und einen Parser als Sensor.

    03Verlässliche Ausgaben: LLMs und Modelle

    Assistenten wie Copilot schreiben Codezeilen. Dieses Kapitel geht eine Ebene höher: Das LLM schreibt das Modell, und ein Generator schreibt den Code. Was Modelle, Sprachen und Generatoren sind, erklärt Teil 1; hier geht es darum, wie der Teil des LLMs verlässlich wird. Das Beispiel ist das aus Teil 1: eine kleine Bibliothek mit Büchern, Mitgliedern und Ausleihen.

    Sprachmodelle, die Modelle schreiben

    Eine Modellierungssprache ist eine Sprache wie jede andere, also kann man sie einem LLM ohne neues Training beibringen: einige Beispielmodelle in den Prompt geben (Few-Shot) und es bei Bedarf in der Sprachreferenz nachschlagen lassen (RAG) [BDMN+24]. Die Beispiele hier nutzen CD4A, eine kompakte Textnotation für UML-Klassendiagramme (siehe Teil 1). 2024 haben wir so eigene GPTs gebaut; hier eine ihrer Antworten, aus der Zeit, bevor die Bibliothek unser Beispiel wurde:

    Probieren Sie die Assistenten selbst aus:

    • CD4A Class Diagram Creator ↗Klassendiagramme in CD4A
    • GUI-DSL2 Model Creator ↗Seitenmodelle in GUI-DSL 2
    • SysML v2 Model Creator ↗SysML-v2-Modelle
    • MontiCore Expert ↗Fragen zu MontiCore

    LLMs, die auf eine Modellierungssprache angepasst sind, können mehr als neue Modelle erstellen: Sie können bestehende ändern oder eine Whiteboard-Skizze in die passende Syntax überführen. Beim Ändern ändern sie allerdings manchmal Dinge, nach denen niemand gefragt hat — und reparieren manchmal nebenbei Fehler [NKR+25]. So oder so muss etwas das Ergebnis prüfen.

    Danach prüfen: der Parser

    Verlässlich wird das erst durch das, was nach dem LLM passiert. Ein Parser — derselbe, den der Generator nutzt — prüft jedes Modell. Scheitert es, geht das Modell mit der Fehlermeldung des Parsers zurück an das LLM, und das LLM versucht es erneut:

    Das ist die Harness-Idee aus Kapitel 02, angewandt auf Modelle: Der Parser ist ein Sensor. Er findet jeden Syntaxfehler — aber erst hinterher, und jeder neue Versuch kostet Zeit.

    Vorab verhindern: Constrained Decoding

    Syntaxfehler lassen sich auch während der Erzeugung verhindern. Ein LLM schreibt Token für Token — also kann eine Grammatik vor jedem Token jeden Kandidaten streichen, der an dieser Stelle nicht folgen kann. Das heißt Constrained Decoding. Am einfachsten sieht man es an JSON: Nach einer öffnenden Klammer darf nur ein Schlüssel in Anführungszeichen oder eine schließende Klammer folgen.

    Die Kandidaten hier sind schematische lesbare Fragmente, keine tatsächlichen Tokenizer-Einheiten. JSON braucht Anführungszeichen, Doppelpunkte, Kommas und gültige Werte, nicht nur geschlossene Klammern. Der Reiter CD4A zeigt denselben Mechanismus mit der Grammatik einer Modellierungssprache und baut die Klasse Book der Bibliothek. Für verschachtelte Klammern führt die Grammatik Buch darüber, was noch offen ist — genau dort sind LLMs schwach: Selbst ChatGPT hat Mühe, Klammern in langen Texten richtig zu schließen [1].

    Fallstudie: Grammar Masking für CD4A. Wir haben das mit kleinen offenen Modellen ausprobiert, die auf einem einzelnen Rechner laufen, an rund 1.000 Modellierungsaufgaben [NRR24]:

    Mit Masking steigt die Parser-Akzeptanz auf 87–93 % statt 0,3–42 %. Unser MontiCore-→-Lark-→-Guidance-Prototyp von 2024 erreichte keine 100 %: Konvertierte Grammatikkonstrukte wichen vom Zielparser ab; Tokenlimits und endlose Wiederholungen verursachten weitere Fehler. Läufe am Tokenlimit sind aus der Tabelle ausgeschlossen. In diesem Guidance-Aufbau dauerte die Erzeugung 13–30-mal so lange; das ist kein allgemeiner Aufwand von Constrained Decoding. Semantische Wohlgeformtheit und Anforderungen brauchen eigene Prüfungen.

    Die Maske braucht Kontrolle über die Schleife, die Token für Token erzeugt. Bei offenen Modellen hat man sie selbst. Gehostete APIs übernehmen inzwischen einen Teil davon: Mehrere garantieren Ausgaben nach einem JSON-Schema, und die API von OpenAI nimmt für eigene Werkzeuge auch eine kontextfreie Grammatik an [23].

    Für NeugierigeWarum die Maske eine Garantie ist
    • Warum es eine Garantie ist. Ein Parser danach kann nur ablehnen; die Maske entscheidet vorher. Mit korrekter Constraint-Implementierung, exakter Zielgrammatik und regulärem Ende in einem akzeptierenden Zustand gehört die Ausgabe zur erzwungenen Grammatik. Abschneiden und Konvertierungsfehler verletzen diese Voraussetzungen; Syntax allein belegt keine Semantik [24].
    • Tokens passen nicht zur Grammatik. Ein Token kann ein halbes Schlüsselwort enthalten, oder eine Klammer plus Leerzeichen plus den nächsten Namen. Die Maske kann deshalb nicht einfach Grammatiksymbole nachschlagen; sie prüft für jeden Kandidaten, ob seine Zeichen den bisherigen Text fortsetzen können. Das bei jedem Schritt für Zehntausende Tokens schnell zu tun, ist der Ingenieursteil.
    • Syntax, nicht Bedeutung. Unter diesen Voraussetzungen sichert die Maske syntaktische Akzeptanz. Ob die Klassen die richtigen sind oder eine referenzierte Klasse überhaupt existiert, braucht weiter Prüfungen danach — und das Modell kann in gültigen, aber ungeschickten Text gedrängt werden, wenn es eigentlich etwas anderes „wollte“.

    Vom Modell zur Anwendung

    Zusammen mit modellgetriebener Softwareentwicklung reicht das bis zum Ende: Nutzer beschreiben ihre Domäne informell, ein LLM leitet das Klassendiagramm ab, Syntax- und Semantikprüfungen validieren das Modell, und ein Generator wie MontiGem macht daraus einen lauffähigen datenzentrierten Web-Prototyp [Net24]:

    Das LLM macht nur, was es gut kann: Sprache in ein Modell übersetzen. Reproduzierbare Generierung kann auch Vorlagenfehler reproduzieren. Geschäftsregeln, Abläufe, Berechtigungen und Integrationen können weitere Modelle und Erweiterungen erfordern. Exakte Grammatikkonvertierung, Zeitlimits, Kontextbedingungen und Generatorwartung bleiben Engineering-Aufgaben. Das explizite Zwischenmodell lässt Menschen prüfen, was die KI verstanden hat — bevor auch nur eine Zeile Code existiert.

    Kurz gesagt

    • Ein LLM setzt Text fort, Token für Token, jedes aus einer Wahrscheinlichkeitsverteilung gezogen.
    • Es schreibt den plausiblen Text, nicht den wahren — rechnen Sie mit selbstsicheren Fehlern, etwa Paketen, die es nicht gibt.
    • RAG, Agenten und Harnesses entstehen rund um das Modell; viel von der Qualität eines Agenten steckt im Harness.
    • Prüfen gehört in den Harness: Tests, Linter, Parser.
    • Ein korrekter Decoder kann bei regulärem Abschluss Syntax gemäß der erzwungenen Grammatik garantieren; Semantik und Anforderungen bleiben eigene Prüfungen.
    LOHNT SICH, WENN
    • die Ausgabe in einer formalen Sprache vorliegt — JSON, eine DSL, Code —, die ein Parser oder eine Grammatik prüfen kann
    • ein Programm auf der Ausgabe aufbaut
    ETWAS ANDERES REICHT, WENN
    • der Text nur für Menschen ist: Dann reicht eine sorgfältige Durchsicht durch einen Menschen
