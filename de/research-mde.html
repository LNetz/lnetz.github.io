Software aus Modellen: was DSLs, Modelle und Generatoren sind — und wie aus einem Klassendiagramm eine laufende Webanwendung wird.

Sie haben schon modelliert — vielleicht ohne es so zu nennen. Eine Tabellenkalkulationsformel beschreibt eine Rechnung, die die Tabelle ausführt. Ein SQL-CREATE TABLE beschreibt Daten, die die Datenbank dann speichert. Ein JSON-Schema beschreibt ein Formular, das eine Bibliothek dann zeichnet. Jedes Mal haben Sie in einer kleinen, spezialisierten Sprache aufgeschrieben, was Sie wollen, und eine Maschine hat daraus Verhalten gemacht. Wer Power Apps, einen Formular-Baukasten oder einen OpenAPI-Codegenerator benutzt hat, hat modellgetriebene Werkzeuge benutzt.

„Ein Modell ist eine Abstraktion eines Originals, gemacht und genutzt für einen Zweck.“

nach Herbert Stachowiak, 1973 · [DGM+21]

Modellgetriebene Softwareentwicklung macht daraus die Methode: Die wichtigen Entscheidungen über ein System werden als Modelle aufgeschrieben, und Generatoren machen aus den Modellen Code — immer wieder, sobald sich die Modelle ändern. Dieser Artikel erklärt die drei Bausteine — Modelle, die Sprachen, in denen sie geschrieben sind, und die Generatoren, die sie lesen — und zeigt dann, wie weit sie tragen: Aus einem Klassendiagramm wird eine laufende, datenzentrierte Webanwendung mit Datenbank, Server und Seiten — ein Anfang, der mit seinen Anforderungen wächst, statt weggeworfen zu werden. Ein kleines Beispiel zieht sich durch alles: eine Bibliothek, die Bücher an ihre Mitglieder verleiht.

01Modelle und Sprachen

Bevor etwas generiert werden kann, muss etwas aufgeschrieben werden — und zwar so, dass eine Maschine es lesen kann. Dieses Kapitel handelt vom Was: von Modellen und den Sprachen, in denen sie geschrieben sind.

Was ist ein Modell?

Ein Modell bildet etwas ab, es lässt etwas weg, und es dient einem Zweck. Herbert Stachowiak hat diese drei Merkmale 1973 benannt — Abbildung, Verkürzung und Pragmatik —, und sie sind bis heute der beste Test für jedes Modell [1]. Ein Liniennetzplan ist ein Modell einer Stadt: Jeder Punkt steht für eine echte Haltestelle (Abbildung), Straßen und Hügel fehlen (Verkürzung), und was bleibt, ist genau das, was man braucht, um durch die Stadt zu kommen (Zweck). Eine Wanderkarte derselben Stadt behält die Hügel und lässt die Haltestellen weg. Keine ist „richtiger“ — jede taugt für etwas anderes.

Die nützliche Frage an ein Modell ist deshalb nie „Ist es vollständig?“, sondern „Wofür ist es da?“. In der Software kann das Original etwas sein, das existiert — ein Geschäftsprozess, eine bestehende Datenbank — oder etwas, das erst gebaut werden soll: Das Modell eines Systems beschreibt es, bevor es da ist.

Modell

Ein Modell beschreibt ein Original, ein reales System oder eine Entität, die existiert oder künftig existieren soll. Ein Modell ist eine Abstraktion des Originals. Ein Modell hat einen Zweck in Bezug auf das Original. [2]

Für NeugierigeArten von Modellen
  • Beschreibend oder vorschreibend. Ein Modell kann beschreiben, was ist (eine Analyse des heutigen Prozesses), oder vorschreiben, was sein soll (der Entwurf des Systems von morgen). Vorschreibende Modelle sind die übliche Eingabe, wenn eine Implementierung generiert wird; aus beschreibenden lassen sich trotzdem Berichte, Visualisierungen oder Dokumentation erzeugen.
  • Explizit oder programmiert. Ein Text- oder Diagrammmodell ist explizit; ein Modell kann auch implizit in einem Programm stecken — jedes Programm enthält eines.
  • Modellbasiert oder modellgetrieben. In der modellbasierten Entwicklung unterstützen Modelle einzelne Tätigkeiten; in der modellgetriebenen Entwicklung treiben sie den Prozess, Modelle sind die primären Artefakte.
  • Viele Modelle. Jedes Modell erfasst nur einige Aspekte seines Originals; ein System wird deshalb durch eine Menge von Modellen beschrieben.
  • Zwei berühmte Einzeiler sagen dasselbe wie Stachowiaks Verkürzung: „Alle Modelle sind falsch, aber manche sind nützlich“ (George Box) [3] und „Die Karte ist nicht das Gebiet, das sie darstellt“ (Alfred Korzybski) [4].

Klassendiagramme in 60 Sekunden lesen

Der Großteil dieses Artikels arbeitet mit einer Art von Modell: dem Klassendiagramm. Es beschreibt die Arten von Dingen in einer Domäne und wie sie zusammenhängen. Eine Klasse ist eine Art von Ding (Book, Member); ein Attribut ist ein Feld, das jedes solche Ding hat (ein Titel, eine Seitenzahl). Eine Linie zwischen zwei Klassen ist eine Assoziation: Die beiden gehören zusammen. Die Zahlen an ihren Enden sagen, wie viele — 1 genau eins, * beliebig viele. Das reicht, um das laufende Beispiel dieses Artikels zu lesen: eine kleine Bibliothek, die Bücher an ihre Mitglieder verleiht.

Dasselbe Modell lässt sich als Text schreiben. CD4A ist MontiCores textuelle Sprache für Klassendiagramme:

classdiagram Library {
  class Book {
    String title;
    int pages;
    boolean available;
  }
  class Member {
    String name;
  }
  class Loan {
    Date due;
  }
  association [1] Member -> (loans) Loan [*];
  association [*] Loan -> (book) Book [1];
}

Sprachen für Modelle: DSL vs. Allzwecksprache

Java, Python oder C# können jedes Programm ausdrücken — sie sind Allzwecksprachen. Eine domänenspezifische Sprache (DSL) tauscht diese Allgemeinheit gegen Nähe zu einer Domäne: Sie bietet deren Begriffe direkt an und lässt vieles andere weg, sagt aber, was sie sagen kann, kurz und in den Begriffen der Domäne. Einige kennen Sie schon: SQL für Daten, HTML für Dokumente, CSS für Layout, Tabellenformeln für Berechnungen, reguläre Ausdrücke für Textmuster. Eine DSL kann weniger sagen als Java, aber was sie sagen kann, sagt sie in wenigen Zeilen — und in Worten, die auch Menschen außerhalb der IT schon benutzen [5].

Echte Systeme werden mit mehreren kleinen Sprachen beschrieben, je eine pro Aspekt: eine für die Daten, eine für die Seiten, eine für die Regeln, eine dafür, wer was sehen darf. Jede bleibt einfach, weil sie eine Aufgabe hat — und sie passen zusammen, weil sie auf dieselben Namen verweisen.

Für NeugierigeArten von DSLs
  • Intern oder extern. Eine interne DSL lebt in einer Wirtssprache (eine flüssige Java-API); eine externe DSL hat eine eigene Syntax und einen eigenen Parser [6]. Die Sprachen in diesem Artikel sind extern.
  • Text oder Grafik. Fachleute sind im Text oft schneller. Die Endnutzer eines Projekts bevorzugten trotzdem das grafische Klassendiagramm, sobald es mehr als 120 Klassen hatte [BGK+24]. Gute Werkzeuge bieten beide Sichten auf ein Modell.
  • Woraus eine Sprache besteht. Aus ihrer Syntax (wie Modelle aussehen), ihrer Semantik (was sie bedeuten) und ihrer Pragmatik (wie man sie für ihren Zweck einsetzt).

Das Bild ist nicht das Modell

Ist das Modell der Text oder das Diagramm? Weder noch. Text und Diagramm sind zwei konkrete Arten, das Modell zu zeigen. Werkzeuge arbeiten auf seiner abstrakten Syntax: den Elementen des Modells und ihren Beziehungen, gehalten als Datenstruktur. In MontiCore ist diese Struktur ein Baum — der abstrakte Syntaxbaum (AST) —, den ein Parser aus dem Text baut und die Symbolauflösung dann über Namen verknüpft; andere Frameworks halten einen Objektgraphen, der zu einem Metamodell konform ist. Ein Diagrammeditor zeigt dieselbe Struktur als Kästen und Linien; Tippen und Zeichnen ändern dasselbe Modell. Deshalb ist es einem Generator egal, ob Sie getippt oder gezeichnet haben.

Deshalb wird auch in Stufen geprüft. Erstens: Ist der Text überhaupt lesbar — nimmt der Parser ihn an? Zweitens: Sind alle Namen bekannt — gibt es jedes erwähnte Book? Drittens: Sind die Regeln eingehalten — zum Beispiel keine zwei Attribute mit demselben Namen? Die Grammatik beantwortet nur die erste Frage. Der Rest sind Kontextbedingungen: Regeln, die jedes gültige Modell einhalten muss, von Hand gegen den Baum geschrieben.

Über Namen verweisen Modelle auch aufeinander. Ein Seitenmodell sagt Book und meint die Klasse im Datenmodell — über die Symboltabelle, ein Verzeichnis aller benannten Elemente, auch über Dateien und Sprachen hinweg. Das Seitenmodell hält einen Verweis, keine Kopie: Wird Book umbenannt oder gelöscht, melden die Werkzeuge den Verweis als unaufgelöst, statt still eine veraltete Kopie zu behalten. Und Grammatiken können mehr als prüfen: Sie können auch einschränken, was ein LLM schreibt, Token für Token — siehe Grammar Masking in Teil 2.

Für NeugierigeSprachen für Sprachen

Ein Modell ist konform zu seiner Sprache, und die Sprache ist durch eine Grammatik (wie in MontiCore) oder durch ein Metamodell definiert, ein Modell der abstrakten Syntax einer Sprache. MontiCore leitet aus jeder Grammatik intern eine solche Beschreibung ab, als Klassendiagramm. Davon zu trennen ist das ist Instanz von zwischen Objekten und Klassen: Das Objekt anna : Member ist eine Instanz der Klasse Member; das Klassendiagramm selbst ist konform zu CD4A. Und was ein Modell bedeutet, ist eine dritte Frage: seine Semantik, eine Abbildung in eine semantische Domäne.

02Vom Modell zum Code

Auch ohne Generierung sind Modelle nützlich: zum Verständigen, zum Analysieren, zum Prüfen eines Entwurfs, bevor er gebaut wird. Die Entwicklung treiben sie erst an, wenn ein Programm sie liest und systematisch etwas daraus ableitet: Code, andere Modelle, Tests, Dokumentation. Dieses Programm ist ein Generator.

Was ein Generator tut

Am Anfang steht das Problem. In einer typischen Geschäftsanwendung taucht dieselbe Datenstruktur immer wieder auf: als Datenbanktabelle, als Serverklasse, als Transferobjekt, als Modell im Browser, als Formular. Das alles von Hand zu schreiben ist mühsam und fehleranfällig — und es ist schematisch: Wer die Datenstruktur kennt, könnte den Rest fast blind tippen. Genau das lässt sich generieren.

Die meisten Generatoren arbeiten wie ein Serienbrief. Eine Briefvorlage hat Platzhalter, und eine Adressliste füllt sie, ein Brief je Adresse. Ein Code-Template ist der Zielcode mit Lücken, und das Modell füllt die Lücken:

Das Modell trägt die Domäne, die Templates tragen die Technik: Tauscht man die Templates — und die Laufzeitteile, auf die sie bauen —, kann dasselbe Modell Code für eine andere Plattform erzeugen. Und eine Modellzeile erreicht jede Schicht auf einmal. Probieren Sie es — ergänzen Sie Attribute an Book:

Vielleicht haben Sie solche Generatoren schon benutzt. Prisma leitet aus einer Schemadatei Datenbanktabellen und einen typisierten Client ab; OpenAPI Generator macht aus einer API-Beschreibung Clients, Server und Dokumentation. Die Generatoren in diesem Artikel arbeiten genauso, mit einem Unterschied, der zählt: Sie laufen nicht einmal zum Start, sondern immer wieder, bei jeder Änderung am Modell.

Ein echter Generator kann mehr als Templates füllen. Er liest das Modell und prüft es, transformiert es in eine Struktur, die näher am Ziel liegt — und ergänzt dabei etwa eine id, die niemand modelliert hat —, und erst dann generiert er. Ein Blick hinein:

Generator

Codegenerierung ist die Übersetzung eines Quellmodells in Artefakte einer ausführbaren Sprache. [2]

Für NeugierigeIn echten Generatoren
  • Warum ein Zwischenbaum. Liegen Eingabe- und Ausgabesprache weit auseinander, lohnt es sich, den AST der Eingabe zuerst in einen zu transformieren, der zur Ausgabe passt.
  • Ein Modell, mehrere Bedeutungen. Dasselbe Modell lässt sich verschieden abbilden: Ein Zustand Off kann eine Enum-Konstante, eine Ganzzahl, eine Unterklasse oder eine Methode werden. Deshalb muss die Bedeutung geklärt sein, bevor ein Generator gebaut wird.
  • Konfigurierbare Generatoren. Templates lassen sich an Hook-Punkten ersetzen, und Generatoren sollten weglassen können, was ein Projekt nicht nutzt — ungenutzte generierte Endpunkte sind ein Sicherheitsrisiko [BGK+24].
Für NeugierigeMontiCore, das Werkzeug, das die Werkzeuge baut

Woher kommen die Sprachen CD4A, GUI-DSL und OCL/P mit ihren Parsern, Symboltabellen und Prüfungen? Aus MontiCore, einer Language Workbench, die an der RWTH Aachen seit 2004 entwickelt wird [9]. MontiCore baut die Werkzeuge, die Ihre Modelle lesen: Aus einer Grammatik generiert es den Parser, die Baumklassen, die Symboltabelle und den Rahmen für die Regelprüfungen; die Sprachingenieurin ergänzt die Regeln, der Werkzeugbauer Transformationen und Templates. Seine Stärke ist Komposition: Sprachen werden aus Sprachen gebaut — die GUI-DSL verweist über Symbole auf CD4A, OCL/P bettet eine Ausdruckssprache ein. So konnte MontiGems Sprachfamilie wachsen, ohne neu geschrieben zu werden.

Generierter und handgeschriebener Code

Vollständige Generierung ist selten: Echte Systeme mischen generierten und handgeschriebenen Code — die Geschäftsregel, die kein Modell abdeckt, die besondere Maske, die Anbindung an ein Altsystem. Die Regel, die das möglich macht, ist einfach: Generierten Code nie bearbeiten. Der nächste Generierungslauf überschreibt ihn. Ein einmaliges Gerüst ist trotzdem ein brauchbarer Start — aber nur ein Generator, der wieder laufen kann, hilft einem System weiter, dessen Modelle sich weiter ändern [DGM+21].

Stattdessen baut handgeschriebener Code auf dem generierten auf. MontiCore und MontiGem nutzen dafür den TOP-Mechanismus: Gibt es eine handgeschriebene Klasse Loan, nennt der Generator seine eigene Klasse LoanTOP, und die handgeschriebene Klasse erweitert sie. Der Rest des Systems benutzt weiter den Namen Loan und bekommt die handgeschriebene Fassung.

Der Preis ist klein, aber real: Der Generator muss nach handgeschriebenen Dateien suchen, also generiert man nach dem Anlegen oder Löschen einer solchen Datei einmal neu. Und der Trick hat eine Grenze: Seitenmodelle sind Bäume, keine Klassen, es gibt also nichts zu erweitern — wie Seiten stattdessen angepasst werden, zeigt der Abschnitt zu CD2GUI. Die Lehre aus fünf Projekten ist eindeutig: Ein Codegenerator muss handgeschriebene Erweiterungen unterstützen [BGK+24].

Für NeugierigeGeneration Gap und andere Mechanismen
  • Das allgemeine Muster. TOP ist eine Variante des Musters Generation Gap: generierten und nicht generierten Code durch Vererbung trennen, zuerst beschrieben von John Vlissides [10]. Partielle Klassen in C# lösen dasselbe Problem ohne Vererbung.
  • Andere Mechanismen. Delegation, oder „geschützte Bereiche“ in generierten Dateien, die der Generator in Ruhe lässt — Letztere sind fragil [11].
  • Getrennte Ordner. Handgeschriebener und generierter Code liegen in getrennten Verzeichnisbäumen. Viele Projekte halten generierten Code aus der Versionskontrolle heraus und generieren ihn bei jedem Build neu; andere checken ihn ein, um zu sehen, was der Generator geändert hat — eine Frage des Arbeitsablaufs, kein Gesetz.
  • Kein Round-Trip-Engineering. Code fließt nie ins Modell zurück: Das Modell bleibt die Quelle, der Code wird immer abgeleitet.

Wenn sich das Modell ändert

Neu generieren ist für den Code sicher. Ein laufendes System hat aber auch Daten, und die wurden in der Form des alten Modells gespeichert. Ändert sich das Modell, wird der Code einfach neu generiert, aber die schon gespeicherten Daten müssen womöglich umgewandelt werden:

Datenbankwerkzeuge ziehen dieselbe Linie: Prisma generiert eine Migration für die neue Struktur, und die neuen Spalten aus den alten zu füllen, ist ein Schritt, den man selbst in diese Migration schreibt. Modelle also auf Wachstum anlegen: Ergänzungen lassen sich meist leichter auffangen als Änderungen an Bestehendem — doch auch ein neues Attribut braucht eine Migration, wenn die schon gespeicherten Datensätze einen Wert dafür haben müssen.

Für NeugierigeModellevolution in Praxis und Forschung

Die Praxis bestätigt die Faustregel: In MaCoCo kosteten Ergänzungen an den Modellen weniger Zeit als Änderungen, die auch handgeschriebenen Code berührten und im Datenmodell Datenmigrationen in der laufenden Anwendung nötig machten [DGM+21]. Die Forschung geht einen Schritt weiter: zwei Versionen eines Modells nicht Zeile für Zeile, sondern nach ihrer Bedeutung zu vergleichen — was kann das neue Modell ausdrücken, was das alte nicht konnte? Damit befasst sich meine Arbeit zur Evolution von Domänenmodellen [BNR+25].

03Ganze Anwendungen aus einem Modell

Modellgetriebene Techniken werden weit über Geschäftssoftware hinaus eingesetzt — in eingebetteten und cyber-physischen Systemen, Software-Produktlinien, der Systemanalyse. Ab hier bleibt dieser Artikel bei datenzentrierten Webanwendungen, an denen sich die Ideen am klarsten zeigen, und bei einer Werkzeugkette, MontiCore und MontiGem. Die Teile fügen sich zusammen: ein Generator, der aus einem Klassendiagramm eine Webanwendung macht, eine Sprache für ihre Seiten, eine Transformation, die die Seiten selbst ableitet — und was das alles mit Low-Code und KI zu tun hat. Am Ende des Kapitels stehen eine Fallstudie aus der Praxis und das, was der Ansatz kostet.

Warum sich Geschäftsanwendungen wiederholen

Denken Sie an die Software, mit der Verwaltungen arbeiten: Finanzen, Personal, Inventar, Ausleihen. Listen, Formulare und Detailseiten über einer zentralen Datenbank — und im Kern immer dieselben vier Operationen: anlegen, lesen, ändern und löschen, kurz CRUD. Solche Informationssysteme sind groß, aber ihre Struktur wiederholt sich mit jeder Klasse des Datenmodells. Wahrscheinlich haben Sie das schon genutzt gesehen: Djangos Admin liest die Modelle einer Anwendung und baut daraus Verwaltungsseiten, gedacht allerdings als internes Werkzeug, nicht als die Anwendung selbst; der Scaffold-Generator von Rails schreibt mit einem Befehl Modell, Controller, Views und eine Datenbankmigration für eine Ressource — einmal, als Startpunkt zum Weiterbearbeiten von Hand.

MontiGem — der MontiCore-based Generator for Enterprise Management — geht den ganzen Weg. Das Klassendiagramm ist das einzige Pflichtmodell [GMN+20]; Seitenmodelle, Regeln und Zugriffs-Tags können hinzukommen. Daraus generiert es eine vollständige, datenzentrierte dreischichtige Anwendung — eine Datenbank mit Zugriffsschicht, einen Java-Server, ein Angular/TypeScript-Frontend — und generiert sie immer wieder neu, wenn sich die Modelle ändern, mit getrennt gehaltenem handgeschriebenem Code wie oben. Weil alle Schichten aus einem Modell stammen, passen ihre Schnittstellen per Konstruktion zusammen. Was ein Klassendiagramm nicht sagt — Geschäftsregeln, Abläufe, Anbindungen an andere Systeme —, kommt über weitere Modelle oder handgeschriebene Erweiterungen hinzu.

Seiten beschreiben: die GUI-DSL

Seiten bekommen eine eigene Sprache. Ein GUI-DSL-Modell beschreibt eine Seite als Baum: Eine Seite enthält Karten, eine Karte hat Kopf und Rumpf, der Rumpf enthält Tabellen, Knöpfe, Beschriftungen [GMNR21]. Und es verweist über Namen in das Klassendiagramm — die Symboltabelle bei der Arbeit. Das ist ein ganzes Seitenmodell, leicht vereinfacht — in MaCoCo bekommt eine Seite ihre Daten meist über eine eigene View-Model-Klasse:

webpage Books(all Book b) {
  card {
    head { label "Books" }
    body {
      datatable { rows <b {
        column "Title", title
        column "Pages", pages
}}}}}

all Book b lädt alle Bücher; rows <b macht eine Tabellenzeile pro Buch; column "Title", title zeigt das Attribut title aus dem Klassendiagramm. Daten, Seite und Regeln, jede in ihrer eigenen Sprache, landen auf einem Bildschirm:

CD2GUI: vom Klassendiagramm zur Anwendung

Seitenmodelle müssen immer noch geschrieben werden. CD2GUI nimmt auch diesen Schritt ab: Aus einem Klassendiagramm leitet es die Seitenmodelle selbst ab. Sein Ergebnis ist kein Code, sondern wieder Modelle — eine Modell-zu-Modell-Transformation —, die MontiGem dann zu Code macht, als hätte sie jemand von Hand geschrieben. Für jede Klasse gibt es eine Übersichtsseite (alle Objekte in einer Tabelle) und eine Detailseite (ein Objekt mit Attributen und Assoziationen), dazu ein Dashboard für alle Klassen [GMN+20].

Modelltransformation

Eine Modelltransformation wird auf ein oder mehrere Quellmodelle angewendet und überführt sie in ein oder mehrere Zielmodelle. [2]

Wenn sich Anforderungen ändern: Titel und Exemplare

Eine generierte Anwendung ist ein Anfang, nicht das Ende. Angenommen, die Bibliothek merkt, dass Book zwei Dinge vermischt: den Titel im Katalog und die Exemplare im Regal. Exemplare sollen einzeln verfolgt werden, und kein Exemplar darf zweimal gleichzeitig verliehen sein. Das Modell ändert sich — available wandert in eine neue Klasse BookCopy, und eine Ausleihe verweist jetzt auf ein Exemplar:

classdiagram Library {
  class Book { String title; int pages; }
  class BookCopy { boolean available; }
  class Member { String name; }
  class Loan { Date due; }
  association [1] Book -> (copies) BookCopy [*];
  association [1] Member -> (loans) Loan [*];
  association [*] Loan -> (copy) BookCopy [1];
}

Neu generieren bringt die Tabellen, Serverklassen und Transferobjekte für Exemplare und, über CD2GUI, ihre Übersichts- und Detailseiten, mit den Exemplaren eines Buchs auf dessen Detailseite. Drei Dinge bringt es nicht. Die Regel „eine offene Ausleihe pro Exemplar“ steht in keinem Klassendiagramm: Sie braucht eine OCL/P-Invariante oder eine handgeschriebene Prüfung — und eine Möglichkeit, offene von zurückgegebenen Ausleihen zu unterscheiden, die das Modell noch nicht hat. Der Ausleihablauf — ausleihen, zurückgeben, erinnern — ist handgeschriebener Code oder weitere Modelle über den generierten Seiten. Und die schon gespeicherten Ausleihen verweisen auf Bücher, nicht auf Exemplare: Eine Migration muss die Exemplare anlegen und die Ausleihen neu verknüpfen. Weggeworfen wird trotzdem nichts: Die Anwendung wird um das neue Modell herum neu generiert, und nur die handgeschriebenen Teile, die die Verfügbarkeit eines Buchs berührten, müssen angepasst werden.

Wohin das führt: Low-Code und KI

Low-Code-Plattformen versprechen Anwendungen ohne Programmierung. Aus Sicht von MDE sind viele von ihnen ein bekanntes Rezept: eine Modellierungssprache hinter den Assistenten, dazu fertige Bausteine und eine Plattform, die das Ergebnis ausführt — auch wenn die Sprache nie beim Namen genannt wird [12]. Der Formular-Designer ist ein Seitenmodell, die Datenquelle ist ein Klassendiagramm. Die Plattformen unterscheiden sich darin, was sie mit den Modellen tun: Manche generieren Code, wie MontiGem; andere interpretieren die Modelle, während die Anwendung läuft. Beides ist modellgetrieben.

Schreiben Fachleute ihre Software jetzt selbst? Dasselbe wurde für COBOL versprochen [6], und Low-Code-Sprachen wachsen mit der Zeit gern zu vollständigeren Sprachen zurück. Die realistische Rolle für Citizen Developer ist die von Mitautorinnen der Modelle — und darauf soll dieser Artikel vorbereiten.

Und dann ist da KI. Das Modell zu schreiben ist der Schritt, der noch Fachwissen braucht — und genau dabei kann ein LLM helfen: die Domäne in einem Satz beschreiben, das LLM schreibt das Klassendiagramm, und CD2GUI und MontiGem machen den Rest, deterministisch. In unseren Experimenten von 2024 schrieb GPT-4, ohne jeden Kontext nach einem CD4A-Modell gefragt, in 20 Versuchen kein gültiges. Ein vorgegebenes Gespräch, das die wichtigsten Regeln der Sprache erklärte, hob das bei einer Aufgabe auf 99 von 100; Beispiele statt Erklärungen erreichten 88 von 100 [NMR24]. „Gültig“ heißt, dass der CD4A-Parser das Modell angenommen hat — ob es die richtige Domäne beschreibt, ist eine andere Frage, die der Parser nicht beantworten kann; sie bleibt bei der Fachexpertin.

Wie ein LLM funktioniert, wie es eine Modellierungssprache lernt und wie eine Grammatik es davon abhält, ungültige Modelle zu schreiben, ist Thema von Teil 2 dieser Reihe: KI-getriebene Softwareentwicklung — weiter mit Sprachmodelle, die Modelle schreiben.

Fallstudie: MaCoCo und vier weitere Domänen

MontiGem entstand nicht am Whiteboard, sondern in einem laufenden System. MaCoCo, das Management-Cockpit, mit dem Lehrstühle der RWTH ihre Finanzen, ihr Personal und ihre Projekte verwalten, begann als handgeschriebene Anwendung; Generierung kam Aspekt für Aspekt hinzu, nach einer Methode mit 16 Aktivitäten [DGM+21].

MaCoCo in Zahlen [GLM+24] — Code und Modelle mit Stand März 2022, Nutzer zum Zeitpunkt des Berichts:

74,59 %des Implementierungscodes generiert
500.573generierte Zeilen
73 · 74Domänenklassen · GUI-Modelle
1.403Nutzer an 188 Lehrstühlen und Instituten

Der Anteil vergleicht Codezeilen: 500.573 generierte gegen 170.505 handgeschriebene; die 14.251 Zeilen Modelle zählen nicht mit (mit ihnen wären es etwa 73 %). Er misst, wie viel des Codes generiert ist — nicht, wie viel Aufwand gespart wurde. Und er heißt nicht „generiert statt handgeschrieben“: Jede Seite besteht aus generiertem Basiscode, der von Hand erweitert und optimiert wird.

Nach etwa drei Jahren wurde der Generator aus MaCoCo in ein eigenes Framework herausgelöst, MontiGem, und in vier weiteren Domänen eingesetzt [BGK+24]: Werkzeugverfolgung für Handwerksbetriebe mit Ford, Energiemanagement von Gebäuden, die Datenschutzerklärungen von Wearables (InviDas) und die Entwicklung von Windkraftanlagen (ADD). Was die fünf Projekte gelehrt haben, steht unten unter Was es kostet und Wann sich dieser Ansatz lohnt; mehr auf der MontiGem-Projektseite.

Was es kostet

Nichts davon gibt es umsonst. Die Kosten sind technische Abwägungen, und die fünf MontiGem-Projekte zeigen, wo sie liegen [BGK+24]:

  • Eine Vorleistung. Sprachen, Generatoren, Templates und Laufzeitumgebung müssen gebaut sein, bevor sie sich auszahlen — deshalb zählt ihre Wiederverwendung über Projekte hinweg. Einen Generator in ein laufendes System nachzurüsten ist noch schwerer, hat sich aber langfristig gelohnt.
  • Zwei Dinge zu pflegen. Modelle und Generator entwickeln sich gemeinsam: Jedes Projekt brachte neue Muster, die ins Werkzeug mussten.
  • Fehlersuche über Schichten. Ein Fehler kann im Modell, in einer Transformation, einem Template, im generierten Code oder in der Laufzeitumgebung stecken. In den Projekten blieb das beherrschbar, solange die Abbildung vom Modell auf den Code geradlinig war.
  • Grenzen der Erweiterung. Generierte Teile müssen ersetzbar sein, wo sie auf bestehende Systeme treffen, und sehr spezielle Masken schreibt man besser ganz von Hand.
  • Fachwissen. Jemand muss gut modellieren und jemand die Sprachen pflegen können; in allen fünf Projekten waren MDE-Fachleute dabei.

Kurz gesagt

  • Ein Modell ist eine zweckgerichtete Vereinfachung eines Originals: Fragen Sie, wofür es da ist, nicht ob es vollständig ist.
  • Das Bild ist nicht das Modell: Hinter Text und Diagramm steht eine Struktur, die Werkzeuge prüfen können (in MontiCore ein Baum) — und „es parst“ heißt nicht „es ist richtig“.
  • Eine DSL verzichtet auf Allgemeinheit, um nah an einer Domäne zu sein; einige benutzen Sie schon.
  • Ein Generator arbeitet wie ein Serienbrief für Code und trägt Architekturentscheidungen: Eine Modellzeile wird zu stimmigem Code in jeder Schicht.
  • Generierter und handgeschriebener Code bleiben getrennt, damit jederzeit neu generiert werden kann — der Wert liegt im wiederholten Generieren, nicht in einem einmaligen Gerüst.
  • CD2GUI und MontiGem machen aus einem Klassendiagramm einen laufenden, datenzentrierten Prototyp, der zum vollwertigen System wächst, ohne weggeworfen zu werden.
  • Viele Low-Code-Plattformen sind MDE mit einer Plattform und einer freundlicheren Oberfläche; KI passt davor: Das LLM schreibt nur das Modell, ein deterministischer, testbarer Generator macht den Rest.

Der zentrale Gewinn ist nicht, dass Modelle Code erzeugen können. Er ist, dass fachliche Entscheidungen über das ganze Leben eines Systems explizit, prüfbar und wiederverwendbar bleiben: Wenn Modelle, Generatoren und handgeschriebene Erweiterungen sich gemeinsam entwickeln, kann ein erster Prototyp zur vollwertigen Anwendung wachsen, ohne seine Modelle aufzugeben.

LOHNT SICH, WENN
  • die Anwendung datenzentriert ist und sich um CRUD dreht
  • Beteiligte sich früh durch Prototypen klicken sollen — die zeigen Probleme in Anforderungen und Datenstrukturen sehr früh
  • das Team Beispiele und Dokumentation hat: Modellieren zu lernen dauert nicht lange, selbst für ungeübte Studierende
ETWAS ANDERES REICHT, WENN
  • Kunden sehr spezielle Masken wollen — generierte Seiten waren großartig für Prototypen, nicht für solche Anforderungen
  • die Bedienung ungewöhnlich ist; native Apps waren dort besser
  • niemand im Team gut modellieren kann: Das Ergebnis ist nur so gut wie das Datenmodell

Was fünf Projekte mit MontiGem gelehrt haben [BGK+24].
